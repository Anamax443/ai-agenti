An agent for incoming invoices

Eleven steps from an e-mail to a payment order. The model touches three of them — it recognises that this is an invoice, and transcribes its contents twice independently. It must not pay it.

The path through the system

01 · CODE
Receiving the message
A webhook from the mailbox. Keyed on the message ID; a repeated delivery is discarded.
02 · MODEL
Intent recognition
Is this an instruction to pay, or something else? The answer is one of five values, not free text.
03 · CODE
Extracting the attachment
The PDF or image into storage. The type is checked from the contents, not from the extension.
04 · MODEL A
Transcribing the document
OCR into a fixed structure: supplier, account number, amount, variable symbol, due date.
05 · MODEL B
An independent transcription
A second model, the same document, no knowledge of the first one's result.
06 · CODE
Comparing the fields
Agreement on the account number, amount and symbol is compared character by character. Not by a model.
Gate 1 The transcriptions differ in some field → a question into the chat with a crop of the document. The invoice waits until a person states the correct value.
07 · CODE
Matching the supplier
The account number against the approved list. The account decides, not the company name — that can be written any way at all.
08 · CODE
Checking the limit
The amount against the supplier's cap and against the monthly total.
Gate 2 An unknown account, an amount over the limit, or a second invoice with the same symbol → approval in the chat. With no answer within 72 hours the task is dropped and announced.
09 · CODE
The payment order
A write to the banking API. The idempotency key comes from the invoice number — running it twice does not pay twice.
10 · CODE
Writing to the records
The invoice, both transcriptions, the gate decisions, the result. What a person corrected is stored too.
11 · CODE
Confirmation
A message into the chat. It always goes out — even when the process crashed, especially then.

Step 02 decides what runs. Steps 04 and 05 turn an image into text. The model does nothing beyond that. The decision to “pay” is taken in none of them.

Scenarios

CodeTriggerWhat happens
S1An e-mail with an attachmentThe path above. Ending: paid, or waiting at a gate.
S2The question “did we pay X?”A read from the records. Read only, no write.
S3A document submitted by hand from the chatEnters S1 from step 03.
S4The Sunday digestWhat went through, what is waiting, what crashed.
—Anything elseIt does not improvise. It forwards to a person with a note that it did not recognise the intent.

The list is closed. Extending it means adding a scenario and a process for it — not giving the model more freedom.

Gates by reversibility

ActionIf it gets it wrongMode
Putting an invoice in the queueDeleted in a secondAutomatic
Payment to an approved account within the limitThe supplier returns the moneyAutomatic
Payment to a new accountThe money is goneApproval
Payment over the limitRecovery, not correctionApproval
Changing the supplier listOpens the way for all the restApproval
Answering a status questionNothing, it only readsAutomatic

The middle column determines the right-hand one. Not how much the model is trusted — a payment to an approved supplier goes through on its own because it can be undone.

Memory

  • Durable — the supplier list, limits, permissions. In the repository, versioned.
  • Factual — the history of invoices and payments. In the database.
  • Working — the one invoice it is processing right now.
  • Not stored — banking access. That is held by a different layer.

When it crashes

  • The error reaches the chat within a minute. Silence is not an allowed state.
  • An undelivered transcription is retried three times, then escalates.
  • A bank outage holds the queue; it does not discard it.
  • The log records why the agent decided as it did, not only how it turned out.
