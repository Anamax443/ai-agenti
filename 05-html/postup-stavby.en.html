Eight phases. Each has one goal, concrete steps and a gate — the list of conditions that must hold before you start the next one. The phases are not skipped; each removes one class of mistake that the following one would otherwise run into.

00 00:00:00 → 00:45:00 ~45 min
Blocks everything else

Get the transcript of the show

Until the transcript exists there is no way to decide what the agent should look like. Everything from phase 6 onwards rests on what was actually said in the interview.

  1. Finish the running whisper-ctranslate2, or start again with the medium model
  2. Verify that a .txt was produced and that the Czech text makes sense
  3. Read the result through and fix garbled names and terms
  4. Note down which passages caught your attention, and why

Gate

  • The transcript exists and is readable
  • Proper nouns are corrected
  • You have written down what you want to take away from the interview

The last point is not a formality. Twenty different conclusions can be pulled out of an hour of speech; without your selection what comes out is generic mush.

02 01:30:00 → 04:30:00 ~3 h

Preflight as the first module

The checks are written before the function they guard. Otherwise they get postponed to the end and never written at all.

  1. preflight.py — twelve checks per the brief, each returning a Check
  2. Every finding carries a remedy: a ready command to copy
  3. FAIL blocks the run, WARN only informs
  4. Test it on a machine without the libraries — a second workstation, say

Gate

  • A missing library is noticed within a second, not after five minutes
  • An unreachable Hugging Face gets its own message, not a generic timeout
  • Every red finding offers a command to fix it

This is the thing that was missing in the console: the model did not download and nothing said so. Preflight is the answer to exactly that situation.

03 04:30:00 → 07:30:00 ~3 h

The transcription core, still without a window

A working pipeline driven from the command line. It keeps the model in memory, reports progress through a callback, and can be interrupted.

  1. validators.py — existence, size, extension, audio stream via PyAV
  2. transcriber.py — a class holding the model, callback (text, percent)
  3. downloader.py — yt-dlp with a progress hook
  4. A threading.Event check at every segment

Gate

  • Transcribing a 40-minute recording runs from the console
  • A second run does not download the model again
  • A non-existent file fails before the model is loaded
04 07:30:00 → 11:30:00 ~4 h

The window and progress reporting

The GUI is only a display. All the work runs on a background thread and communicates through a queue — widgets are never touched from the worker thread.

# message flow
worker ──put──> queue.Queue ──after(100)──> GUI
               status | progress | log | phase | done | error
  1. The state machine per chapter 7 of the brief
  2. Progress from segment.end / info.duration
  3. Remaining-time estimate as a moving average over 10 segments
  4. Segments into the log as they arrive — you see straight away whether the language is right

Gate

  • The window does not freeze even while the model loads
  • Interrupt stops the run within five seconds
  • No exception takes the window down
05 11:30:00 → 13:30:00 ~2 h

Package it into an EXE

A portable folder that can be copied onto a machine without Python.

  1. build.ps1 — PyInstaller --onedir --windowed
  2. --collect-all for ctranslate2, av, faster_whisper, tokenizers, onnxruntime, yt_dlp
  3. Test it on a machine that has never had Python on it

Gate

  • The EXE starts on a clean Windows
  • Preflight passes green there
  • A transcription runs through to the end

The bundle comes out at over 300 MB. That is the price of the native CTranslate2 libraries and there is nothing sensible to be done about it.

06 13:30:00 → 18:00:00 ~4.5 h
The design waits on phase 00

Turn the transcript into knowledge

A raw transcript is verbose material. This phase turns it into something you can come back to — a structured extract via an LLM.

  1. Split the transcript into blocks of ~8 thousand characters with overlap
  2. Extraction via Claude Haiku: topics, claims, names, recommendations
  3. Output as JSON against a schema, not free text
  4. Store it in D1 alongside the original transcript and the timestamps

Gate

  • A structured extract comes out of the interview
  • Every claim carries a timestamp so it can be traced
  • The result can be compared with your own notes from phase 00

Exactly what gets extracted will be decided from the content of the interview. The structure above is an estimate, not a final schema.

07 18:00:00 → ??:??:?? open-ended
The design waits on phase 00

An agent over a library of transcripts

Only here does it make sense to talk about agent architecture — once there is something to build from and it is clear which principles from the interview you are adopting.

  1. An RSS watcher: new episodes transcribe themselves
  2. Search across the library of transcripts
  3. A decision about orchestration — what the agent does alone, where it asks
  4. Feedback: what worked, fed back into the prompts

Gate

  • A new episode appears in the library without your intervention
  • A query across the transcripts returns an answer with a source and a timestamp

I am not writing this phase out any further yet. I have not heard the interview, so I would be inventing an architecture on guesses about what was said in it. Once you send the transcript, we rewrite phases 06 and 07 against the real content.
