How we build AI agents that can actually be run

Not an experiment, and not a tool purchase. A specification for designing, building and deploying an agent in a way that keeps it supervisable.

AI recognises. Code executes.

The model gets three jobs only: work out what is being asked, pull structure out of text, write text. Everything with consequences — writing to a system, making a payment, sending something out — is ordinary program code that no model reasons about.

Why this matters

Outcome 1

The process fails and reports it. Someone knows within minutes.

Outcome 2

The process succeeds. The result is the one that was specified.

The third outcome is removed by design. An agent that decides for itself how to carry out a task can succeed, fail — or do something nobody asked for. That third branch is the source of every “the assistant emailed fifty people” story. This way of building has nowhere to get it from.

What it means operationally

Cost Deterministic code costs a fraction of what a model costs. The order-of-magnitude difference is not which model you pick, but how much work you hand it at all.
Accountability Every irreversible action has a named mode: on its own / within a limit / with approval. The deciding factor is how reversible the mistake is, not how much you trust the model.
Identity Who may do what is bound to the channel (phone number, ID, signature), never to a name in the text. Anyone can write “this is the director” — but not from the director's number.
Oversight A kill switch that takes one action. A crash is reported to a person, not to a log. Agent silence must be distinguishable from “there was nothing to do”.
Regulation The agent discloses that it is an AI whenever it communicates outward. The AI Act requires it, and in practice it works better than the alternative.

The process — nine phases, each with a gate

F0design
F1real data
F2skeleton
F3backbone
F4model
F5gates
F6kill switch
F7deploy
F8operate

A gate is a list of conditions at the end of a phase. Until all of them hold, the next phase does not start. The three highlighted ones are never skipped — verification on real data (F1), a process with two outcomes before any model is involved (F3), and a working kill switch (F6). When these are missing, you find out from the damage.

Evidence that this is more than a document

Specification applied to our own running agent (JobWatch, 30 Aug 2026)

  1. The kill switch did not stop anything. The Stop button closed the run record, but processing carried on and kept sending messages.
  2. A crashed run was silent. Notifications were sent only on findings, so “found nothing today” and “crashed today” looked identical from outside. The agent could have been dead for a week.
  3. Third-party text reached the model unwrapped. Text written by unknown people fed the scoring step with no defence of any kind.

All three defects were present in a system with 38 passing automated checks. Tests ask whether a function returns the right value. A gate asks whether the system does what it promises — and that is a different question.
